# Bookshelf — Microservices

## Почему микросервисы?

Монолит стал узким местом: Монолит удобен на ранних этапах разработки: все компоненты находятся в одном приложении, между ними легко вызывать методы и выполнять общие транзакции. Однако по мере роста системы увеличивается связанность компонентов, усложняется разработка и становится сложнее независимо изменять и масштабировать отдельные части приложения.
В этом проекте монолит разделяется на микросервисы в учебных целях, чтобы на практике изучить принципы микросервисной архитектуры. Каждый сервис будет отвечать за отдельную бизнес-область и сможет независимо разрабатываться, тестироваться, деплоиться и масштабироваться. При этом взаимодействие между сервисами будет происходить через API, что позволит на практике столкнуться с особенностями распределённых систем: сетевыми ошибками, таймаутами, отказами сервисов, согласованностью данных и необходимостью централизованного мониторинга.

## Архитектура

- **auth-service** (порт 8081) — регистрация, авторизация, управление пользователями
- **books-service** (порт 8082) — каталог книг, рецензии
- **auth-postgres** (порт 5432)
- **books-postgres** (порт 5432)
- **frontend** (порт 5173)

Каждый сервис имеет свою базу данных (Database per Service).

## Компоненты системы

| Компонент | Назначение |
|-----------|-----------|
| auth-service | Аутентификация и пользователи |
| books-service | Книги и рецензии |
| auth-postgres | БД для auth-service |
| books-postgres | БД для books-service |
| frontend | React-приложение |

## auth-service
domain/user.go — структуры User, AuthResponse, RegisterRequest
handler/auth_handler.go — регистрация, логин
service/user_service.go — бизнес-логика аутентификации
repository/user_repository.go — работа с таблицей users
Таблица users в отдельной базе auth_db

## books-service
domain/book.go, domain/review.go — структуры Book, Review
handler/book_handler.go, handler/review_handler.go — CRUD API
service/book_service.go, service/review_service.go — бизнес-логика
repository/book_repository.go, repository/review_repository.go
Таблицы books, reviews в отдельной базе books_db

## Асинхронная обработка

### Новые компоненты

- **RabbitMQ** — очередь сообщений для асинхронных задач
- **MinIO** — S3-совместимое хранилище для обложек книг
- **worker-service** — фоновый обработчик задач из очереди

### Сценарий обработки обложки

1. Пользователь загружает изображение → books-service сохраняет оригинал в MinIO
2. books-service публикует сообщение в RabbitMQ
3. worker-service забирает сообщение, обрабатывает изображение (resize)
4. worker-service загружает результат в MinIO и обновляет статус в БД

### Почему асинхронно?

Обработка изображений — тяжёлая операция (1-5 секунд). Если делать синхронно,
пользователь будет ждать. Асинхронный подход: пользователь сразу получает ответ
"обложка обрабатывается", а результат появляется в фоне.

## API Gateway

### Роль API Gateway

API Gateway — это единая точка входа для клиентских приложений в backend-систему. Вместо того чтобы обращаться напрямую к каждому микросервису, frontend отправляет запросы на Gateway, который определяет целевой сервис и перенаправляет запрос.

Такой подход скрывает внутреннюю структуру системы от клиента и позволяет централизованно управлять общей логикой обработки запросов. При добавлении новых сервисов или изменении их внутренних адресов frontend не должен менять адреса всех backend-сервисов.

### Ответственность Gateway

Gateway централизованно реализует следующие сквозные функции:

- **CORS** — управление разрешёнными источниками, HTTP-методами и заголовками запросов.
- **Rate limiting** — ограничение частоты запросов для защиты сервисов от чрезмерной нагрузки и злоупотреблений.
- **Structured logging** — структурированное логирование запросов, HTTP-статусов, времени обработки и других диагностических данных.
- **Caching** — кэширование подходящих ответов для уменьшения нагрузки на backend и ускорения обработки повторных запросов.
- **Routing** — маршрутизация запросов к соответствующим микросервисам на основании URL и HTTP-метода.

Gateway также может стать местом централизованной проверки токенов доступа. При этом бизнес-авторизация и проверка прав на конкретные ресурсы остаются ответственностью соответствующих сервисов.

### Архитектура

В проекте `bookshelf` API Gateway располагается между frontend и backend-микросервисами.

```text
                    ┌──────────────────┐
                    │     Frontend     │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │   API Gateway    │
                    │     :8000        │
                    └────────┬─────────┘
                             │
                  ┌──────────┼──────────┐
                  │          │          │
                  ▼          ▼          ▼
          ┌────────────┐ ┌──────────┐ ┌───────────────┐
          │auth-service│ │books-    │ │worker-service │
          │   :8081    │ │service   │ │    :8083      │
          │            │ │  :8082   │ │               │
          └────────────┘ └──────────┘ └───────────────┘
```

Frontend обращается только к Gateway. Внутренние адреса микросервисов используются на стороне backend-инфраструктуры и не должны быть известны клиенту.

Gateway направляет запросы следующим образом:

| Маршрут | Целевой сервис |
|---|---|
| `/api/v1/auth/*` | `auth-service:8081` |
| `/api/v1/users/*` | `auth-service:8081` |
| `/api/v1/books/*` | `books-service:8082` |
| `/api/v1/reviews/*` | `books-service:8082` |

`worker-service` выполняет фоновые задачи, например обработку и сжатие обложек книг. Он взаимодействует с очередью сообщений и необходимыми хранилищами. Его внутренние рабочие операции обычно не требуют публичного HTTP-маршрута через Gateway. Если сервис предоставляет клиентские HTTP-эндпоинты, они добавляются в маршрутизацию отдельно.

### Пример работы

**Без API Gateway**

Frontend должен знать адрес каждого сервиса и самостоятельно обращаться к нему:

```text
Frontend ──► auth-service:8081/api/v1/auth/login
Frontend ──► auth-service:8081/api/v1/users/me
Frontend ──► books-service:8082/api/v1/books
Frontend ──► books-service:8082/api/v1/books/123/reviews
```

При изменении адресов сервисов или добавлении общей логики обработки запросов frontend может потребовать изменений.

**С API Gateway**

```text
Frontend ──► gateway:8000/api/v1/auth/login
Frontend ──► gateway:8000/api/v1/users/me
Frontend ──► gateway:8000/api/v1/books
Frontend ──► gateway:8000/api/v1/books/123/reviews
```

Gateway самостоятельно определяет целевой микросервис, применяет настроенные сквозные функции и передаёт запрос дальше. Для frontend существует единый адрес входа.

### Преимущества и ограничения

Преимущества API Gateway:

- единая точка входа для клиентских запросов;
- сокрытие внутренних адресов и структуры микросервисов;
- централизованная настройка CORS, ограничений частоты запросов и логирования;
- возможность кэширования подходящих ответов;
- упрощение изменения и масштабирования backend-инфраструктуры.

При этом Gateway становится дополнительным компонентом, который необходимо поддерживать и масштабировать. Он не заменяет бизнес-логику, проверки прав доступа внутри сервисов, внутреннюю коммуникацию микросервисов или обработку фоновых задач.

### Принятое архитектурное решение

В проекте `bookshelf` используется API Gateway как единая HTTP-точка входа для frontend. На Gateway централизуются маршрутизация, CORS, rate limiting, structured logging и кэширование там, где оно безопасно и оправданно. Микросервисы сохраняют ответственность за бизнес-логику, работу с данными и специфичные для домена проверки.
